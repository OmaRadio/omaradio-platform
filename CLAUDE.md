# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

OmaRadio is an Omarchy-Linux-focused pirate radio platform (in-universe: broadcasting via "Transmitter-One" from the Falkland Islands), streaming at https://OmaRadio.stream. It aims to be a fully-autonomous platform: AI DJ staff producing on-air segments, Creative Commons music, and community news, with an underlying streaming server and infra to actually get it on the air.

This repo (`omaradio-platform`) is currently **early-stage and mostly scaffolding**: the infra/deploy side (getting `cliamp-server` running on the transmitter host) is real and working, and `pipeline/dj-segment/` (see below) is a first, small slice of the AI production pipeline. `scheduler/`, `www/`, and most of `staff/` are still placeholder directories with no code yet. Don't assume implementation exists just because a directory does — check before referencing.

Read `README.md` for the directory layout and `The-Spirit-of-OmaRadio.md` for the full editorial/tone guidelines and platform role definitions (Orchestrator, Station Manager, DJ, Intern, IT Guy) before doing any content/staff-persona work. Two rules from there worth internalizing directly:
- Resources are tight — be efficient, resourceful, and frugal in what you build/spin up.
- Any destructive action or any action with real-world cost (cloud resources, etc.) must be surfaced to the Orchestrator (the human) for an explicit go/no-go **before** it's enacted — this repo's own guidelines reinforce the general Claude Code confirmation norms, don't skip it here.

## No build/test/lint commands (yet)

There is no repo-wide package.json, go.mod, or CI config. `scheduler/src`, `scheduler/db/migrations`, and `www/` are still empty — don't invent commands for them; set up tooling as part of whatever work first adds real code there.

The one piece of real, runnable infrastructure besides the pipeline below is `cliamp-server` (the streaming server), an **external** Go project (`bjarneo/cliamp-server`, vendored/pinned by tag) — its build lives in this repo's `deploy/Makefile`, not as source here.

### `pipeline/dj-segment/` — AI DJ segment pipeline (MVP)

The first real application code in this repo: generates one AI-written, locally-TTS'd DJ segment at a time, gated behind Orchestrator approval, and documents getting it on air. Python, run via `uv run <script>.py` — each script carries its own PEP 723 inline dependency block, so there's no repo-level `requirements.txt`/`pyproject.toml` and no manual install step. Full walkthrough (setup, usage, the manual on-air runbook): `pipeline/dj-segment/README.md`.

- `generate_segment.py --dj <slug> --brief "..."` — builds a prompt from `The-Spirit-of-OmaRadio.md` + the persona (`staff/stations/<station>/djs/<slug>/persona.{toml,md}`), calls the Anthropic API (`claude-sonnet-5` by default) for a structured `{title, est_seconds, script}`, then renders it to MP3 via local `kokoro-onnx` (no TTS API cost) + ffmpeg, with EBU R128 loudness normalization (`LOUDNORM_TARGET_LUFS`, currently -12 to match this library's actual mastering — measured empirically, not a generic convention, see the constant's comment for how to re-measure). Needs `ANTHROPIC_API_KEY` in a repo-root `.env` (see `.env.example`) and the Kokoro model weights (~350MB, gitignored, fetched separately — see README). `--dry-run` sanity-checks the assembled prompt with no API call.
  - `--dj` isn't DJ-exclusive: it also matches other staff personas by the `slug` field inside their `persona.toml`, for singular-per-station roles (`station-manager/`, `intern/`) that don't have a `djs/`-style slug subfolder — see `find_dj_dir()`. Used sparingly, per that persona's own boundaries.
  - `--news-item <id|latest>` (repeatable) + `--list-news` — pulls stored `pipeline/news-intern/` output in as factual grounding for a segment; `--brief` stays required and sets angle/tone/how prominently each item features (a segment isn't forced to be "about" the news item — could be a passing mention). See `pipeline/news-intern/` below.
- `review_segment.py {list,show,approve,reject}` — the approval gate. Nothing `generate_segment.py` writes reaches the media library (and therefore can never sync or air) until `approve` copies it into `$LOCAL_LIBRARY/dj-segments/<dj>/generated/`; `reject` never touches the library.
- **`generate_outros.py`** — generates a small, fixed-size pool (12-14, default 13, via `--count`) of short, generic **station**-identification one-liners (e.g. "You're listening to OmaRadio One"), deliberately **not** tied to any DJ's voice or personality — first built per-DJ, then reworked 2026-09-05 once it became clear a per-DJ outro can't correctly promise who (if anyone) comes on next (a periodic DJ like Vera lands in a different block-owner's territory each of her three daily slots). Rendered in one dedicated `STATION_VOICE` (`bf_emma` — unclaimed by any staff persona, a neutral "network ID" read, not a character) and written into `$LOCAL_LIBRARY/jingles/station-outro/` — the existing `jingles` media category, not `dj-segments/`, since this is station branding rather than a DJ's own content (paired `.mp3` + `.script.json` per line). Deliberately **not** gated behind `review_segment.py` — brief-independent generic filler, no per-item approval step (still printed to stdout in full at generation time for a human to eyeball). One Claude call (default `claude-haiku-4-5`, same cheap-tier reasoning as Alan's topic-brief calls) requests the whole batch at once with a structured-output uniqueness check (exact count, no duplicate lines) and one retry on validation failure. Re-running **replaces** the whole pool from scratch (old files deleted first) rather than accumulating across runs. `build_playlist.py`'s `_maybe_append_station_outro()` (see below) is what actually decides when one of these airs.
- **Station outro splicing** (`build_playlist.py`'s `plan_block()`) — after every DJ segment placed into a block (both a shift-owner's normal pick and a periodic DJ's single insertion, e.g. Vera's), there's an independent, weighted chance (`STATION_OUTRO_CHANCE`, per-station like `STATION_PERIODIC_SEGMENTS`, currently `{"one": 0.75}` — missing station = disabled) of splicing in one station outro from the shared pool, as its own separate on-air entry (`"type": "outro"`, `"dj": null`) rather than audio-concatenated into the segment file itself — simpler, and cliamp-server just plays whatever's next in `on-air/`'s sorted order regardless. Deliberately **not** every time — a station ID after literally every segment reads as repetitive fast. Picked via `pick_playable()` with its own anti-immediate-repeat tracking (one shared `last_outro`, since it's one pool now, not per-DJ). No pool yet just means segments air without one (a single warning per block-plan run, not per segment). `"outro"` entries are deliberately excluded from `n_segments`/the email's per-DJ segment-title rundown (different `"type"`, and `"dj": null` besides) but do count toward `n_outros` (shown in both the CLI log line and the rebuild email/Pushover) and toward total block duration like everything else. **Complementary, not redundant**, with a platform-wide rule added to `The-Spirit-of-OmaRadio.md`'s DJ role section (2026-09-05): every DJ segment's own script must end with its own short, in-character sign-off line handing back to the regular program (e.g. "now on to some music") -- that's baked into `generate_segment.py`'s prompt automatically (the Spirit doc is read live, no code change needed) and gives every segment a natural close regardless of what follows, while the station outro above is a separate, occasional, station-branded stinger that may or may not additionally play right after it.
- **`generate_vera_handoffs.py` + dynamic hand-off tags** (added 2026-09-05) — a third, more targeted mechanism, specific to Vera: since a pre-rendered clip can't dynamically speak a name, this generates small pools (5 lines each, default) of pre-written variants for each *reachable* outcome of her periodic slot -- `dj-mox`, `dj-nova`, or literal `"music"` -- written into `$LOCAL_LIBRARY/dj-segments/dj-vera/handoff/<target>/`. Targets are hardcoded to what today's schedule can actually produce, not every DJ that exists: her hours (0/8/16 UTC) land in the 00:00 (`dj-mox`), 06:00 (open/music), and 12:00 (`dj-nova`) blocks respectively, and the 18:00 (`dj-nikon`) block algebraically never contains one of her insertions -- so there's no `dj-nikon` pool, and none is needed unless the shift/periodic tables change. `build_playlist.py`'s `_maybe_append_handoff()` runs right after her periodic segment is spliced in (before the station-outro roll) and **deterministically** (not weighted -- always applied when a pool exists for the resolved target) picks `target = dj if dj else "music"`, i.e. whichever DJ (if any) already owns the block she's landing in per `owning_dj()`/`STATION_SHIFTS` -- both already known at that exact point in `plan_block()`, so no new state is needed. Rendered in Vera's own real voice/persona (unlike the generic station outro's separate `STATION_VOICE`). Entries get `"type": "handoff"`, `"dj": "dj-vera"` -- folded into `n_outros`/the email's outro count (not split out separately) since it's rare (at most one per block) and conceptually adjacent, but kept as its own `"type"` in the schedule JSON for clarity. Vera's own rundown script stays deliberately generic/non-naming (see her persona.md) precisely because this exists -- she "doesn't know" who's next when her segment is written, so the actual naming happens here, picked at schedule time instead.
- Four DJs exist so far: `staff/stations/one/djs/{dj-mox,dj-nova,dj-vera,dj-nikon}/` — add more by following that directory's `persona.toml`/`persona.md` shape. `dj-vera` is a news-anchor persona (multi-story spoken-only "rundown," built via repeated `--news-item`) scheduled differently from the others — see `STATION_PERIODIC_SEGMENTS` below, not `STATION_SHIFTS`. `dj-nikon` (voice `am_michael`) is a music-knowledge/record-collector persona added to own the 18:00 UTC block, which was previously open/music-only — freeform and personality-driven like Mox/Nova (same `auto_dj.py`/`topics.toml` flow, not Vera's fact-grounded one), just slotted into a specific shift instead of floating across all blocks the way Mox/Nova's pool selection otherwise implies; `plan_block()` needed no code change for this, since shift ownership is pure `STATION_SHIFTS` data. `staff/stations/one/station-manager/` (Alan) and `staff/stations/one/intern/` (Relay) are working examples of non-DJ staff personas wired in the same way.
- **`auto_vera.py`** — hands-off feeder for Vera: fetches news (shells to `fetch_news.py fetch`), computes "unused" items statelessly (scans her own recent `script.json`'s `news_item_ids`, no separate state file), generates via `generate_segment.py`, and **auto-approves with no human review** (`review_segment.py approve --by AUTO-VERA`) — a deliberate, narrow exception to the approval gate above, reasoned as safe specifically because her content is strictly grounded in fetched facts. Stdlib-only, same constraint as `build_playlist.py`, since it runs unattended on transmitter-one. Skips a cycle (no forced generation) when nothing's unused, rather than repeating stale ground. Runs via `deploy/omaradio-vera-auto.timer` at 23:45/05:45/11:45 UTC — **15min before the 00:00/06:00/12:00 block builds**, not her nominal 00/08/16 slot hours, because `pick_latest()` is evaluated once at block-build time (see `STATION_PERIODIC_SEGMENTS` below); the 18:00 block never gets a Vera run since it never contains her insertion.
- **`auto_dj.py` + `topics.toml`** — hands-off feeder for Mox/Nova/Nikon, a materially different problem from Vera's: they're freeform, personality-driven ("each DJ is their own creative director" per the Spirit doc), not news recaps, so there's no "unused item" to point at. Instead, Alan (Station Manager) picks a topic from a human-curated backlog (`topics.toml`, needs periodic restocking by the Orchestrator) and writes an actual brief via one `claude-haiku-4-5` call, then the normal `generate_segment.py`/`review_segment.py approve --by AUTO-{DJ}` flow runs — **also auto-approved, no human review**, a bigger trust step than Vera's since there's no factual grounding to fall back on if tone drifts. `--topic-id` (bookkeeping-only, `generate_segment.py`) records which `topics.toml` entry a segment used, in `script.json`'s `meta`, for the same recently-used exclusion pattern as Vera's news items. Unlike `auto_vera.py`, this one needs the Anthropic SDK directly (PEP-723, `uv run`) since Alan's pick-and-brief step is its own API call. One shared daily timer (`deploy/omaradio-dj-auto.timer`, 10:00 UTC) covers all three DJs in one process (`--all`) rather than per-DJ timers — their content sits in a pool `pick_playable()` cycles randomly across whichever block(s) draw from that DJ's pool (Mox/Nova's owned blocks, or Nikon's owned 18:00 block), so there's no shift-aligned timing *within* a block to hit the way Vera has.
- **Notifications** (email via `RESEND_API_KEY`, Pushover via `PUSHOVER_API_TOKEN`/`PUSHOVER_USER_KEY`, both via `/opt/omaradio/secrets/notify.env`, both independently optional — either/both/neither channel fires per whichever secrets are set, both services no-op quietly per-channel if unconfigured): `send_email()`/`send_pushover()` are duplicated (not shared-imported) into both `auto_dj.py` and `build_playlist.py`, matching this repo's standalone-script convention — plain stdlib `urllib.request` POSTs (Resend's REST API for email, Pushover's for push), deliberately adding **zero new Python dependencies**. Two triggers: `auto_dj.py` notifies when a DJ has `<=2` unused topics left (`LOW_STOCK_THRESHOLD`, resent every run while low — no dedup state, same body on both channels); `build_playlist.py`'s `notify_rebuild()` notifies after every successful `on-air/` rebuild, but with **different bodies per channel** — email gets the full line-by-line rundown (track/segment counts, runtime, DJ segments grouped by DJ with computed approximate air time), Pushover gets a compact per-DJ stats block (segment count, total airtime minutes, approximate start–end UTC window) sized to comfortably clear Pushover's 1024-char message cap rather than a truncated version of the email. **Gotcha, hit for real 2026-09-04**: Resend sits behind Cloudflare, which blocks Python's default `Python-urllib/x.y` User-Agent outright (error code 1010) — identical `curl` traffic went through fine. Fixed by setting an explicit `User-Agent` header on both channels' requests; if this notification path is ever rewritten, don't drop that header. **Also hit for real 2026-09-04**: a custom `NOTIFY_FROM` sending domain (`transmitter-one@notify.omaradio.stream`, replacing the default `onboarding@resend.dev`) 403'd for several hours across three rebuild cycles until the domain finished DNS-verifying in Resend's dashboard — if `NOTIFY_FROM` is ever pointed at a new domain, verify it's showing green/Verified in Resend *before* relying on it, not after.
- Deferred/non-goals (see the pipeline README for the full list): Twitter/X + Discord connectors (web/RSS is built, see below), the Intern role's still-undefined "Screening Rules" (source-list membership is the screening for now), song-credit announcements, genre-aware/DJ-hosted-genre music selection, hands-off automation for Alan's/Relay's own on-air appearances (still manual). On-air placement is now automated for Mox's/Nova's owned shift blocks — see `infra/transmitter/playlist-builder/` below; `on-air-place.sh` remains for one-off manual placements only.

### `pipeline/news-intern/` — Relay's news fetcher (web/RSS-Atom only)

First real piece of Relay's persona-documented-but-previously-unbuilt job. `fetch_news.py {fetch,list,show}` polls Orchestrator-curated `sources.toml` (RSS/Atom via `feedparser`), dedups against `$LOCAL_LIBRARY/../state/news-intern/seen.json`, and writes to `$LOCAL_LIBRARY/news-desk/YYYY-MM-DD/` — `"news"`-category items use the feed's own description directly (free, no API call), `"release"`-category items get one Claude call (default `claude-haiku-4-5`, cheaper than `generate_segment.py`'s default since this is mechanical summarization). No approval gate (research material, not broadcast audio) — reaches the vault via the existing, unmodified `sync-library.sh news-desk` category. Full detail: `pipeline/news-intern/README.md`.

## Streaming infra architecture (`deploy/`, `infra/transmitter/`)

The stack running on the transmitter host ("transmitter-one"):

```
Caddy (:80/:443, Cloudflare DNS-01 TLS) --reverse_proxy--> cliamp-server (:8000) --reads--> station on-air/ symlink farms
```

- **`deploy/Makefile`** — deploys both the vendored `cliamp-server` binary and this platform repo on the transmitter host. Two independent, intentionally different update rhythms:
  - `make cliamp-update VERSION=vX.Y.Z` — deliberate, pinned upgrade of the external `cliamp-server` dependency (cloned into `vendor/cliamp-server`, built, installed to `/usr/local/bin/cliamp-server`, service restarted). Real canonical location on transmitter-one: `/opt/omaradio/vendor/cliamp-server` (source checkout) and `/opt/omaradio/bin/cliamp-server` (build output) — both are `CLIAMP_DIR`/`BIN_DIR`'s plain relative paths (`vendor/cliamp-server`, `bin`) resolved against `/opt/omaradio`, confirming *this* is genuinely where `make` is meant to be run from, matching the `platform/` checkout note below. **Gotcha, hit for real 2026-09-03**: `cliamp-fetch` only `git clone`s `$(CLIAMP_REPO)` when `vendor/cliamp-server` doesn't already exist — if it exists but its `origin` remote points somewhere else (e.g. it predates a fork switch), `make cliamp-update` silently `git fetch --tags`s the wrong remote and never finds the new tag. If `CLIAMP_REPO` ever changes, manually check/fix the existing checkout's `origin` first (`git remote set-url origin $(CLIAMP_REPO)` in `/opt/omaradio/vendor/cliamp-server`) rather than trusting the Makefile to notice.
  - `make deploy` (platform-pull + platform-restart) — pull-and-redeploy this repo freely.
  - `make cliamp-service-install` — one-time systemd unit install; also provisions `/opt/omaradio/stats` (cliamp-server refuses to start without it), installs `config.toml`, and creates the `/opt/omaradio/secrets/cliamp.env` file (holds `ADMIN_PASSWORD`, never committed).
  - **This repo IS checked out on transmitter-one**, at `/opt/omaradio/platform` (remote `origin` = this same `OmaRadio/omaradio-platform` repo) — confirmed 2026-09-03. The Makefile's `SERVICE_SRC`/`CONFIG_SRC`/etc. targets are prefixed `platform/deploy/...` for exactly this reason: run `make` from `/opt/omaradio` (parent of the checkout), not from inside `platform/` itself. **Don't assume this checkout is current** — it had silently gone stale (many commits behind, missed entirely by an earlier check that only looked in the `omaradio` user's home directory instead of `/opt/omaradio/`) until manually caught and `git pull`ed. `cd /opt/omaradio/platform && git pull` is the correct way to update it; nothing does this automatically.
  - `make geoip-install` fetches/installs `GeoLite2-Country.mmdb` from the upstream GeoLite mirror (always latest, not pinned).
  - **`/opt/omaradio/bin/` is transient build/download staging, not a real install location** — confirmed 2026-09-03, after finding a stray root-owned `GeoLite2-Country.mmdb` copy there (cleaned up) that had nothing to do with the actual running service. `cliamp-build` drops the freshly-built binary there before `cliamp-install` copies it to the real `/usr/local/bin/cliamp-server`; `geoip-fetch` drops the downloaded `.mmdb` there before `geoip-install` copies it to the real `/opt/omaradio/geoip/GeoLite2-Country.mmdb`, chowned to `omaradio:omaradio` in that same `install` step. Don't treat anything under `bin/` as authoritative — check `/usr/local/bin/cliamp-server` and `/opt/omaradio/geoip/` instead.
  - **Known ownership wart**: `/opt/omaradio/geoip/` (the directory itself, not the `.mmdb` file inside it, which is correctly `omaradio:omaradio`) ended up `root:root` — `install -D` run under `sudo` created the parent directory as a side effect without applying `-o`/`-g` to it. Harmless for the read-only service, but fix with `sudo chown omaradio:omaradio /opt/omaradio/geoip` if it's ever in the way (e.g. a future `geoip-install` run needing to write there as the `omaradio` user without sudo).
- **`deploy/config.toml`** — cliamp-server config: one `[stations.<id>]` block per station, each pointing at a hand-built, numerically-ordered symlink farm (`.../stations/<id>/on-air/`). `shuffle = false` and `recursive = false` are load-bearing — the ordering scheme depends on both staying off/flat. When copy-pasting a new `[stations.<id>]` block, double-check the header key itself was renamed, not just the fields inside it — TOML silently last-key-wins on a duplicate table header, so a missed rename overwrites the earlier station instead of erroring.
- **`deploy/cliamp-server.service`** — systemd unit; admin password comes from `EnvironmentFile=-/opt/omaradio/secrets/cliamp.env` (leading `-` = optional, so the service still starts, with admin auth disabled, if the secret isn't provisioned yet).
- **`deploy/Caddyfile`** — proxies `tx.omaradio.stream` on both `:80` and `:443` to cliamp-server; both ports are listed explicitly to disable Caddy's automatic http→https redirect, because non-browser stream clients (VLC, cliamp, etc.) need plain `:80` to keep working, while the web player needs `:443`. Per-station path routing (`/one/stream`, `/enigma/stream`) is handled inside cliamp-server itself, not by Caddy.
- **`infra/transmitter/provisioning/init-ubuntu-harden.sh`** — one-time, run-as-root droplet hardening (Ubuntu 24.04): creates the `omaradio` sudo user from the root SSH key, disables root/password SSH login, configures ufw (SSH/80/443 only), enables unattended-upgrades (auto-reboot deliberately left off — a live stream shouldn't restart out from under itself), installs fail2ban.
- **`infra/transmitter/vault/init-omaradio-vault.sh`** — interactive, run-once-per-volume: builds the media vault directory skeleton (`library/`, `schedule/<station>/`, `stations/<station>/on-air/`) on the mounted DO block storage volume. Station list and DJ list are edited directly in the script's `STATIONS`/`DJ_NAMES` arrays. Dated leaf folders (e.g. `schedule/<station>/YYYY/MM`) are deliberately *not* created here — `infra/transmitter/playlist-builder/build_playlist.py` (below) owns those now.
- **`infra/transmitter/vault/sync-library.sh`** — rsyncs local media into the vault's `library/` tree only (never touches the `on-air/` symlink farm, which the playlist builder rebuilds separately). `./sync-library.sh [--dry-run|-n] [category ...]`; categories: `music jingles dj-segments news-desk shoutouts ads number-messages`. Defaults `LOCAL_LIBRARY` to `~/Work/OmaRadio/media_library/library`, overridable via env var.
- **`infra/transmitter/playlist-builder/build_playlist.py`** — stdlib-only Python, runs natively on transmitter-one (not a dev-machine tool) via a systemd timer (`deploy/omaradio-playlist-builder@.timer`, `OnCalendar=*-*-* 00,06,12,18:00:00 UTC`) rather than `uv`/PEP 723 — no third-party deps needed, and that host runs no other Python. Every 6h, rebuilds a station's `on-air/` from already-approved/synced vault content and **reloads** `cliamp-server` (`systemctl reload`, SIGHUP, zero listener disconnection — only works on the `choyer/cliamp-server` hot-reload fork this platform runs, see `deploy/Makefile`'s header comment; `--reload-mode restart` is kept as a fallback if that fork ever misbehaves, but is not the default). Shift ownership is a hardcoded `STATION_SHIFTS` table in the script (station "one": Mox owns 00:00–06:00 UTC, Nova owns 12:00–18:00 UTC, Nikon owns 18:00–00:00 UTC — 06:00–12:00 is the only remaining open/music-only block) — 100% of scheduling logic lives here because cliamp-server itself has none (confirmed via its source: plain lexicographic path sort, infinite loop, no hot-reload of its own). A separate `STATION_PERIODIC_SEGMENTS` table (deliberately not merged into `STATION_SHIFTS` — different keying domain, see its own comment) handles DJs who get exactly one segment inserted at specific UTC hours regardless of block ownership — currently Vera at 00:00/08:00/16:00 UTC (the 18:00 block algebraically never gets one, confirmed not just intended, since her hours are 8h apart and blocks are 6h). `find_periodic_insertions()` computes the offset, and the insertion is spliced into `plan_block()`'s normal build loop once accumulated duration reaches it — picked via `pick_latest()` (most-recent by filename, NOT `pick_playable()`'s random-with-anti-repeat, since a periodic DJ is only picked once per run so that exclusion would be a no-op; most-recent is both simpler and more correct for a "latest news" persona). Writes an audit-trail schedule JSON to `schedule/<station>/YYYY/MM/DD-HHMM.json` before ever touching `on-air/`, and keeps exactly one prior `on-air/` generation as `on-air.prev/` for one-command rollback (see the script's own docstring). Emails a rebuild summary on success — see the notification bullet above. Install via `make playlist-builder-service-install` in `deploy/Makefile` (mirrors `cliamp-service-install`'s pattern) — enables but does not start the timer; starting it is a deliberate separate step. **Gotcha**: its systemd service deliberately omits `NoNewPrivileges=true` (present on `cliamp-server.service`) because it shells out to `sudo systemctl reload cliamp-server` via the same NOPASSWD sudoers rule `on-air-place.sh` uses — that flag would silently break the reload. Does a **full replace** of `on-air/` every run, so any manual `on-air-place.sh` placement survives only until the next 6h boundary.
- **`deploy/omaradio-vera-auto.service`/`.timer`, `deploy/omaradio-dj-auto.service`/`.timer`** — the systemd units for the two hands-off content feeders described above, installed via `make vera-auto-service-install`/`make dj-auto-service-install` (same enable-but-don't-start discipline as every other timer here). Both reuse a single `/opt/omaradio/secrets/dj-segment.env` (holds `ANTHROPIC_API_KEY` and `LOCAL_LIBRARY=/mnt/media_library/library` — pointed straight at the vault, so `approve` writes there directly and neither feeder needs a `sync-library.sh` step). `uv` itself had to be installed for the `omaradio` user for these (transmitter-one's one and only non-stdlib-Python dependency) — it lands in `~/.local/bin`, not a system path, and systemd units don't source shell profiles, so both `ExecStart=` lines **and** every internal `subprocess.run(["uv", ...])` call inside `auto_vera.py`/`auto_dj.py` resolve `uv` via an absolute-path lookup (`find_uv()`) rather than trusting `PATH` — hit for real 2026-09-03 (first deploy failed with `FileNotFoundError: 'uv'` from exactly this gap) before that fix landed. `make notify-service-install` provisions the separate, optional `/opt/omaradio/secrets/notify.env` used by the email notifications above; re-run the two service-install targets after adding it so the (also optional, leading `-`) `EnvironmentFile=` line reaches the live units.

## Repo layout beyond infra

- **`staff/`** — one directory per platform role (`it-guy/`, `stations/<station>/{station-manager,intern,djs}/`). Only station `one` exists so far; `it-guy/` itself is still an empty directory — no dedicated persona has been built there. `djs/{dj-mox,dj-nova,dj-vera,dj-nikon}/`, `station-manager/` (Alan), and `intern/` (Relay) all have real personas (see the pipeline section above).
